The local Node GET route composes lazily over the existing runtime `DATABASE_URL` pool. It authenticates a current owner read/write session and checks origin/fetch metadata before any export read. It returns one complete versioned attachment containing all 38 reviewed public tables under the read-only repeatable snapshot. Operational auth tables are excluded. Raw driver errors are not logged/exposed; there is no partial output or legacy fallback. Unreviewed runtime schemas fail closed, so a deployment must point at a database with the reviewed notebook migrations.

Buffered HTTP delivery is capped at **4 MiB** of serialized JSON (with the existing 100,000-row cap), below [Vercel's documented 4.5 MB function response payload limit](https://vercel.com/docs/functions/limitations). The underlying offline builder still supports its 64 MiB maximum; the actual route deliberately supplies the lower deployment limit. This limit is an implementation capacity choice, not a PRD portability limit. Larger notebooks return `export_size_limit` without any attachment. A complete download beyond this limit requires a later reviewed streaming/chunked delivery path; current route integration does not claim unlimited portability. One large database cell can still exceed in-process capacity before the builder detects it, as recorded in the original contract.

Settings keeps the request same-origin/no-store, creates an object URL only after a successful response with the expected attachment/type, preserves the server's fixed filename, and releases the URL after the browser has had time to consume it. It displays sign-in, size-limit, and generic failure feedback. No password/token or private notebook content is stored in browser persistence by this control. Authenticated browser download behavior on HTTPS remains unverified; synthetic handler tests exercise successful complete delivery and the actual route's enforced size cap.

A session-protected download factory is now prepared in `lib/export/handler.ts`. It requires the configured owner UUID, HTTPS origin, and a valid owner session with read or write permission before reading any notebook rows. Missing/invalid/foreign/revoked sessions fail; capture-secret headers/cookies are not a fallback. Only GET is accepted. Requests provide either the exact configured Origin or same-origin/direct-navigation Fetch Metadata; cross-site and same-site metadata are rejected. Successful downloads have a fixed UTC-date filename, JSON content type, exact UTF-8 Content-Length, no-store, Cookie/Authorization variation, and nosniff. Size/schema/source/auth failures return stable private errors with no attachment or partial data. No existing export route imports this factory; migration 0014 and live integration remain pending.

`buildMemoryExport(postgresExportSource(connection))` reads all 38 reviewed application tables in one checked repeatable-read, read-only transaction. It includes archived objects, source identities/aliases, original snapshots, notes, all observation revisions/reviews/support, normalized text/locators, typed derivations, relationships, capture requests, processing history, receipts, legacy schedules, and saved queries. It does not filter rows through active retrieval eligibility or replace legacy values with new product assumptions.

The JSON envelope contains format `flaneur-memory`, version `2`, schema contract tag `0013`, UTC snapshot time, decoding settings, and a table manifest. Each table has ordered columns with PostgreSQL type/nullability, primary-key column order, and rows in database primary-key order. Each cell is a PostgreSQL textual value or JSON null. This retains large numeric values, JSON numeric precision, timestamp microseconds, arrays, vectors, and binary data without JavaScript number/date coercion. Source `bytea` values use PostgreSQL hexadecimal form, such as `\x00ff`; no gzip decompression or validation replaces original bytes. User text retains Unicode, whitespace, and line breaks. Remote media references are preserved as stored; no remote assets are fetched.

Settings are UTC, `DateStyle = ISO, YMD`, `IntervalStyle = iso_8601`, `bytea_output = hex`, and `extra_float_digits = 3`. Consumers must decode cells using the supplied PostgreSQL column types, rather than guessing numeric/date types from strings. The schema tag identifies the prepared contract; the catalog records the actual column/type manifest. Importing/restoring this format is not implemented or verified.

The default aggregate limits are 100,000 rows and 64 MiB of serialized JSON. Callers can lower these limits. Cursor batches are 100 rows; the complete result is assembled in memory. Limits reject the operation instead of returning truncated tables. This is staging capacity, not a production throughput result or a bound on one unusually large row fetched from PostgreSQL. Missing, duplicate, or new public tables fail review checks; invalid columns/keys, duplicate row keys, obvious credential column names, and malformed values fail. Configured credentials are never loaded by these modules. User-authored content is retained as content, including private notes; this is not a content redaction service.

This data export excludes database DDL, indexes, constraints, sequences, grants/ownership, extensions, and the Drizzle migration ledger. It is a different artifact from an operational database backup.
