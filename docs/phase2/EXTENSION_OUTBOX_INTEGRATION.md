## Capture behavior

Each intentional save receives its own UUID and client capture clock. A message retry reuses that UUID, captured source and exact User words, including whitespace and Unicode. An ambiguous response cannot silently create a second save. Another intentional save, including the same post, gets a separate UUID. The earlier post markers/set that suppressed repeat saves and the unused automatic scrolling implementation are removed. Legacy markers are still stripped by serialization when encountered.

Profile capture no longer scrolls the page automatically or waits for profile completeness. The overlay explains that it saves currently loaded content and that the user can load more and save again. A profile route change before source collection is rejected rather than saving a different page under the old identity display. Post source/URL are frozen when its overlay opens, preserving virtualized feed content if the card is later removed. The note is optional; whitespace-only input becomes no reason, while nonempty note text is preserved exactly.

The overlay awaits local persistence before confirming that a capture is queued on the device. It says that Flaneur has not yet confirmed saving. Only a validated remote acknowledgement or saved receipt permits a server-saved message. Processing queued/running/finished/needs-attention status remains separate from the existence of the saved original. An unknown local request is not represented as saved. Local persistence/message failures keep the same retry payload and freeze its words, preventing an ambiguous retry from overwriting or changing the original. The overlay has modal semantics, a focus loop and return of focus to its invoking control.

Content-side status polling is bounded to twenty checks and stops on saved/blocked/failed status or a disconnected runtime. It is optional feedback, not the delivery mechanism. Later delivery does not require the original LinkedIn tab to remain open. Queue status and explicit retry are available in extension settings without rendering source HTML or exposing the stored capture secret.

## Storage and delivery

The background entry point initializes trusted-context local storage before reading secrets or captured HTML. Its capture handlers accept only this extension's top-frame LinkedIn content-script senders. Queue listing and explicit resume are restricted to the exact extension options page. Messages do not expose the secret or source payload through status responses. Chrome's storage API supports restricting local storage to trusted extension contexts; see the [official storage reference](https://developer.chrome.com/docs/extensions/reference/api/storage).

The browser envelope validator checks supported source/kind, UUID, clock, required fields, credential-free HTTPS LinkedIn URLs, UTF-8/text validity, and both server-aligned limits: 3,000,000 decoded HTML bytes and 4,000,000 encoded JSON bytes. JSON escaping is counted separately. Source data is not silently reduced to fit a queue. Storage quota/access failures cannot return a local queued acknowledgement. Existing source serialization remains in place; this work does not claim a full-page or screenshot capture.

Queue mutations are serialized independently of network work, so another capture can persist while an earlier upload is slow. Only one delivery pump runs per worker instance. It processes at most ten entries and stops claiming new local entries after a 20-second budget; individual HTTP requests retain the existing 15-second timeout. Network/malformed-ack/temporary-server failures retain exact payloads with bounded backoff. A worker restart reconstructs delivery from storage, using the same UUIDs. Every response must satisfy the complete v2 saved acknowledgement contract before cleanup. No parsing or provider work runs in the extension.

An acknowledgement receipt contains only request ID, payload hash, local receipt time and processing state. Following verified server acknowledgement, the storage backend atomically replaces the source entry with a compact receipt marker at the same key, then promotes the receipt and finishes cleanup. This allows the tested full-quota acknowledgement to complete. An interruption before replacement retains the original; an interruption afterward retains the acknowledgement marker, which lookup/recovery can validate without another upload. Receipts do not contain source text or credentials. Changed content under a retained request/receipt ID conflicts. Successful receipt cleanup retains the 200 most recent acknowledgements; older status lookups may be unknown. No unacknowledged source entry is evicted to make room. The local receipt clock and processing snapshot are not independently verified server-time or live processing telemetry.

Missing/rejected authentication blocks automatic retry while retaining source data. Updating the secret does not automatically resume blocked captures; the options page provides an explicit per-capture retry. A generation check prevents an older failed in-flight attempt from undoing a newer explicit resume. Permanent content/payload conflicts remain retained for review rather than automatically changing the capture. Unknown or corrupt storage is reported unavailable without deleting source entries.

The extension uses HTTPS `/api/capture/v2` only, with no fallback to the earlier synchronous capture route. A disabled/unavailable v2 service remains queued; an older deployment returning 404/405 also retains the original for a later compatible deployment. No capture secret or source is sent to an HTTP-configured endpoint. The package adds the `alarms` permission and remains scoped to the configured application origin.

Alarm listeners register synchronously. On install, browser startup and service-worker initialization, the extension checks/recreates the one-minute delivery alarm and resumes due queued captures. Normal capture/resume requests also trigger a pump. The scheduling check preserves an existing alarm instead of repeatedly resetting it. Chrome alarms are best effort and can be delayed or cleared across lifecycle events; a one-minute interval is not a delivery deadline. See the [official alarms reference](https://developer.chrome.com/docs/extensions/reference/api/alarms). Persistent storage and idempotent replay, rather than an assumed service-worker lifetime, preserve capture identity.

## Remaining before activation

The browser fixture injects synthetic runtime responses; it is not an installed-extension test and does not prove real Chrome storage access isolation, service-worker suspension, browser restart, alarm timing, offline recovery or quota accounting. Those installed-extension checks remain next, along with actual options-page accessibility and credential replacement behavior.

The current server gate stays off. Installing the new local extension while it is off will queue captures on the device; it will not activate the v2 server. An existing installed extension is not automatically replaced by a local build. A coordinated rollout still needs the deployed versioned endpoint, an explicit activation decision, verified recurring worker hosting, source/Artifact resolution and supported identity handling. Without an identity proof, the prepared parser may normalize a saved source while leaving identity unresolved. Empty older trail sections still require separately reviewed historical backfill. Restore verification remains deferred.
