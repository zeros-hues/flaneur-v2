Session tokens contain 32 cryptographically random bytes encoded as canonical base64url. The client receives the opaque token; storage receives only its SHA-256 hash and a separate session UUID. Tokens are not JWTs and contain no owner claims. Cookie settings are `__Host-flaneur-session`, Secure, HttpOnly, SameSite Strict, and Path `/`; integration must serve the cookie over a secure origin. Tokens, hashes, cookie values, and authentication exceptions must never be logged.

`issueSession` is a trusted server service to call only after a login provider verifies the notebook owner and grants read/write permission. It does not verify a password, accept an untrusted owner claim, or reuse `CAPTURE_SECRET`. Principals are auth-owner UUIDs, separate from saved Person objects. The prepared store does not implement accounts, identity-provider mapping, or multi-tenant notebook isolation. The issuer must enforce the single notebook's owner policy before granting access.

The user has now chosen private owner-password login. A [salted password provider](OWNER_PASSWORD.md) is prepared, with no actual password/hash configured. It can supply the trusted grant to the session HTTP factory once enrollment, the deployed throttle, migration application, and live integration are completed. The [export download factory](../export/MEMORY_EXPORT_V2.md) is also prepared and accepts only a valid session for the configured notebook owner.

Default expiry is seven days, with caller-selected TTL from one minute to 30 days. PostgreSQL determines creation/expiry times and checks expiry/revocation on every lookup. Write permission permits read and write; read permission cannot authorize a review mutation. Individual revocation leaves other devices active; owner-authorized all-session revocation affects only that principal. Revocation is terminal. Stored session ID/hash/principal/permission/timestamps cannot be rewritten; renewed grants require issuing a new session after appropriate authorization. Cleanup of expired sessions and login rate controls remain integration work.

`sessionAuthorizer(store)` prepares a write-permission callback for `reviewHandler`; it accepts only one exact session cookie. Malformed, encoded, duplicate, or noncanonical tokens fail before a lookup. Capture-secret headers/cookies are not a fallback. Store failures propagate to the handler's private unavailable response. This callback is prepared but not configured in any live route.
