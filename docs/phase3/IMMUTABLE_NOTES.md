# Immutable User note authoring

Implemented locally 2026-10-12. New Person-page notes are User observations rather than mutable legacy `note` rows. Edits use the existing correction service to append a replacement and review, retaining the original text. Exact whitespace/Unicode are preserved; blank-only, malformed Unicode, NUL and oversized input are rejected without truncation or normalization. No real note, schema migration, backfill, deployment or restoration test occurred.

`POST /api/notes` now requires a strict `{ requestId, personId, body }` envelope, owner-session write permission, exact configured HTTPS Origin and JSON. It validates authorization before body parsing, bounds actual streamed bytes to 124,000, and exposes constant private failures. Authored text is capped at 20,000 UTF-16 units. New requests return the observation ID/body with 201; matching retries return the historical receipt with 200. The ID derives from a namespaced request UUID, and changed payload/principal retries conflict. Replaying after a revision/archive neither resets current history nor invalidates newer work.

The PostgreSQL store uses the direct runtime pool and existing processing-scope/graph locks, then a canonical active Person share lock. It appends a User/note/verified authored assertion and invalidates prior object processing heads/jobs atomically. The User support label represents authorship, not a source fact or inferred reason. It does not invent evidence, create an Encounter, start workers, call providers or enqueue guessed replacement work. Existing observations/history remain immutable.

The Person page reads current direct Person User note/reason-for-noticing revisions in a checked repeatable-read read-only transaction. It excludes superseded, explicitly reviewed, individually archived and aliased observations, while retaining the current revision for a historical archived Person page. The result is plain application rows rather than the driver's array subclass. The current capacity is 200 direct authored notes; excess fails explicitly rather than silently dropping notes. Associated Encounter/Artifact notes require their later memory-page presentation and are not guessed into this reader.

The editor uses explicit save/revision buttons instead of blur saving. It renders original spacing, keeps pending request UUID/words fixed on retry, freezes submitted text until cancel, and refreshes the server view after success. A revision sends `correct_observation` with the observed revision ID, so concurrent/stale edits fail instead of overwriting each other. Archived pages offer no editing controls; the server independently rejects new writes to archived/aliased/missing Persons. Read permission alone does not permit a write.

The old `PATCH /api/notes/{id}` no longer updates text in place; authenticated requests receive 410 `immutable_revision_required` without body handling or writes. The obsolete `lib/notes.ts` runtime wrapper was removed. The supplied legacy note store remains only for historical rollback SQL compatibility fixtures and is not imported by a live endpoint. Existing legacy notes render unchanged as preserved earlier notes and are read-only. No opportunistic legacy conversion or bulk backfill was authorized/executed. The prepared planner retains legacy IDs and context-aware subject mapping; those rows must be migrated through that reviewed process before editing through v2 revision history. This is an explicit temporary functional limitation, not a claim that every earlier note is fully migrated.

New authored notes appear on the Person page, in observation inspection/history and the reviewed v2 export. The prepared v2 retrieval reader can consume them when the query pipeline is activated. Current legacy Street search/Walk prompts are not rewritten by this slice to consume every new v2 note; recall/resurfacing cutover remains necessary. New note creation does not treat existing legacy retrieval behavior as correct merely because it is still running.

Validation: all 233 synthetic tests, TypeScript and the production build pass. Five new authoring/HTTP tests cover exact text, idempotent/historical replay, changed retries, unavailable Persons, validation, atomic rollback, authorization before parsing, byte/origin/strict-envelope limits and creation/retry status. Fresh `node scripts/database/validate.mjs --notes-only` through `DIRECT_URL` passed 17 checks using a real read-only wrapper plus actual stores/query bodies over synthetic fixtures: creation/replay/conflict, exact User layer/text, correction/new-current revision, preserved original and legacy rows, no legacy insertion, archive write denial, historical replay and history retention. All fixture changes rolled back and public aggregate counts were unchanged.

The built app passed five HTTP rejection assertions for unauthorized new-note and retired PATCH requests and rejected an unauthenticated foreign-origin request before parsing. No password, valid session, private content or real note was submitted; its loopback server was stopped. Successful authenticated interactive browser editing and the authenticated 410 response were not smoke-tested with real owner credentials. HTTP smoke preceded the result-array normalization; the final production build and SQL checks include that fix. Prior session/identity/archive/export/full SQL baselines remain separate. Restoration verification remains deferred.
