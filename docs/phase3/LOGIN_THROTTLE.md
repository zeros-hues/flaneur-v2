# Shared owner login throttle

Updated 2026-10-12. Migration `0015_shared_login_throttle` was explicitly authorized and committed on Neon dev through `DIRECT_URL`. The ledger has 16 matching entries with no pending migrations; actual-schema throttle validation passed 21 rollback-only checks, and an idempotency rerun applied zero migrations. See [application report](../database/LOGIN_THROTTLE_MIGRATION_0015.md). Live login remains disconnected and the user has not confirmed local password enrollment. `.env` was not modified.

`ownerLoginThrottle` creates the mandatory `allowLogin` callback for `sessionHandler`. The server supplies the owner UUID and policy. A namespaced SHA-256 digest of the canonical UUID identifies one bucket shared by all application instances using the same database. Client headers, addresses, host names, credentials, and cookies cannot choose another bucket. The bucket is an operational auth identity, separate from notebook Person identities.

The default engineering policy admits eight attempts per 900-second fixed window. This is a provisional deployment setting, not a numeric PRD requirement. Configuration permits 1–100 attempts and 60–86,400 seconds. Every admitted attempt counts before password verification, including successful logins. Logout and successful login do not reset the window. Requests rejected by the HTTP envelope never reach password verification.

`postgresLoginThrottleStore` inserts an empty bucket if needed, locks its row, verifies the stored policy, and samples the database clock for the conditional increment/reset. Concurrent creation uses the primary key with `ON CONFLICT DO NOTHING`; subsequent attempts serialize on `SELECT FOR UPDATE`. Expired windows restart with one attempt. At the limit, requests return false without changing the count or extending the window. Statement/lock timeouts bound database work. Store failures and conflicting policies propagate to the handler's generic 503 response; denial produces 429 before password verification. No credential, address, or raw database error is logged.

The table stores only bucket digest, window start, count, and its limit/window policy. SQL constraints enforce key format and bounds. It is in `auth`, excluded from the 38-table public memory export. Operational database backups must include the auth schema; restoration verification remains deferred. No cleanup/reset endpoint is exposed. Policy changes for an existing bucket require a separately reviewed reconciliation of stored policy, rather than an automatic reset that could bypass limits during mixed deployments.

A fixed window allows bursts around its boundary. A shared owner bucket also lets an attacker consume the owner's allowance; edge protection and deployment observability remain integration concerns. This database throttle is not a general request-rate limiter: malformed HTTP requests and unauthenticated logout traffic need deployment protections where appropriate. It does not impose a global concurrent scrypt semaphore. These limits do not prevent preparing the shared login policy, but must be assessed before public route activation.
