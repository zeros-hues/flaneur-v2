# Captured profile identity inspection

Implemented locally 2026-10-12. The Person page now has a separate captured-profile identity inspector and explicit confirm/reject controls. It uses `GET /api/person/{id}/identities`, protected by owner-session read permission and the existing origin policy. Decisions use the existing owner-write `POST /api/review` route. No schema migration, backfill, new Person, automatic merge/reassignment, deployment or real identity decision occurred.

Captures enter this inspection only through recorded noticed-Person Encounter links or historical identity assertions for the selected Person. Names, source URLs and unreviewed keys do not associate a capture automatically. Pages use stable UUID cursors and contain at most 20 captures. The reader checks a repeatable-read read-only transaction; application credentials use the runtime pool, while separate synthetic SQL validation uses `DIRECT_URL`. Current proof filtering matches the identity writers' supported layers/status, canonical active Person/proof references, reviews and revisions. The inspection retains historical noticed links for conflict detection, including archived associations, as the writer does.

The surface shows the capture date, safe original-source link, current proof text/layer and unresolved/associated/conflict/unsupported state. A recorded association is not upgraded merely because it exists. User, Source and Extracted identity assertions remain labeled distinctly. Another Person's current proof is explicitly indicated. Unsafe source links are unavailable, and original gzip/hash values are not returned. This does not present the full captured HTML or recursively browse identity history; stored observation history remains available in the adjacent inspector.

Confirmation requires a supported LinkedIn profile capture with a content hash, an active canonical selected Person, one captured Encounter, at most one current proof, and no prior proof/recorded noticed link pointing at another Person. The user confirms the selected Person by name; arbitrary Person IDs cannot be entered in this control. Multiple active proofs and conflicting associations are not reconciled automatically. A sole current proof for this Person can be rejected through its exact observation ID, including when separate noticed links conflict; rejecting the proof does not delete historical links. Ambiguous or another-Person proofs cannot be rejected from this Person's control. Archived Persons have no identity controls. Eligibility is advisory; the transactional service rechecks every decision and rejects stale requests.

Both actions have an explicit second submit gesture. Pending UUID/action/payload stay fixed for retry while the control remains mounted; errors do not claim success. Confirmation appends the User identity proof, links the captured Encounter, invalidates old generated dependencies and queues the appropriate parse fingerprint atomically. Rejection records the decision, withdraws dependent generated work and fences prior parse work with a null-identity head. Existing history/source/User authorship is retained. No worker was activated; these services already implement queueing. Cancel/navigation after an uncertain response does not prove whether the operation committed; refresh before issuing another decision. Unresolved captures with no recorded Person link or historical Person assertion require a later capture-level selection surface, rather than being guessed into this Person page.
